# ADR 0002 — JWT y segundo factor

**Estado:** JWT implementado; segundo factor TOTP propuesto, todavía no implementado.

## Contexto

HTTP y WebSocket necesitan identificar al usuario y sus roles. Los perfiles de supervisión y administración requieren contemplar un segundo factor; una indicación visual de verificación no constituye una comprobación del servidor.

## Decisión

Usar JWT de acceso y renovación, con claves exclusivamente en variables de entorno, duración por rol y autenticación Bearer para HTTP. El servidor aplica autorización por rol y alcance de instalación. Socket.IO verifica firma, blacklist cuando Redis está disponible y estado/rol actual del usuario en la base.

El diseño contempla un desafío temporal y verificación TOTP antes de emitir acceso definitivo para cuentas con segundo factor. **Ese flujo no está activo:** `auth.service.verify2FA` responde 501, el login omite el desafío y el frontend conserva una simulación. No se debe presentar el sistema actual como protegido por MFA ni dar esa historia por terminada.

## Alternativas y consecuencias

- Sesiones de servidor centralizarían revocación, pero requieren un almacén de sesión compartido.
- JWT permite verificar identidad en ambos transportes; la revocación inmediata depende de Redis y del estado consultado.
- El comportamiento actual degrada si Redis falla: login y logout continúan sin contador/blacklist. Las pruebas cubren esa limitación; no significa que la protección de bloqueo siga operativa sin Redis.
- No incluir contraseñas, hashes, secretos TOTP ni tokens FCM en respuestas públicas o logs. El reset de contraseña también sigue pendiente de implementación.
